# dominion v0.0.2 — plan

Status: done — v0.0.2 is published. This document captured two related efforts:

1. **dominion-client-tui** — a terminal lookalike of the AppImage client.
2. **Clean releases** — publish the server, TUI, APK, and AppImage together.

It exists because GitHub currently has **0 tags and 0 releases**, CI has no
release job, and `get.sh`'s `curl … | sh` path fails without a `latest` release.

---

## Decisions locked

| Question | Decision |
|----------|----------|
| TUI role | Remote client of a running dominion server (true lookalike) |
| Shell pane | In-process suspend + WebSocket attach bridge (no SSH, no embedded VT emulator) |
| TUI stack | `tview` / `tcell` |
| TUI name | `dominion-client-tui` / `dominion-client-tui_<ver>_linux_amd64` |
| TUI distribution | Released alongside the other clients (supersedes the earlier `go install`-only choice) |
| Release mechanism | Scripts are the source of truth; a CI workflow is a thin wrapper around them |
| APK signing | Debug APK (not release-signed) |
| Release layout | One combined `vX.Y.Z` release containing all assets + `SHA256SUMS` |
| Pipeline timing | Lands now for server + TUI + APK + AppImage |
| Architectures | `linux/amd64` only; ARM hosts build from source |
| Bundled Android CA | Canonical project `ca.pem` stored as a repo secret; also published as a release asset |

## Part A — dominion-client-tui

### Deliverable

A new Go command in the same module:

```
cmd/dominion-client-tui/main.go    entry, flag parsing, mode dispatch
internal/tuiclient/api.go          HTTP client: healthz, login/lock/logout, sessions, create/kill
internal/tuiclient/config.go       saved-server + theme, reuses client.json schema
internal/tuiclient/attach.go       WebSocket <-> local terminal bridge
internal/tuiclient/ui.go           tview app: prompt, login, session view, dialogs
```

Built static (`CGO_ENABLED=0`) for `linux/amd64` only, matching the server. The
TUI is a release asset produced by the same pipeline.

### API reuse

It is a **client only** — no server code runs in it. It talks the existing API
and carries the auth cookie in an in-memory `http.CookieJar` across requests and
the WebSocket dial:

| Need | Call |
|------|------|
| reachability probe | `GET /healthz` |
| login / lock / logout | `POST /api/login·lock·logout` (cookie) |
| session list | `GET /api/sessions` |
| create / kill | `POST /api/sessions/create·kill` |
| live shell | `GET /api/attach?session=&cols=&rows=` (WS) |

- `401` bounces to the login screen (`web/app.js:344`, `web/app.js:896`).
- Poll every 3 s (`POLL_MS`).
- The pinned `dominion` session gets no kill action; the server also refuses it
  with `403` (`internal/server/server.go:441`).

### Client capability version (web shells only)

The portal now gates the saved-server screen on a shell capability version
(`dominion-shell/<major>.<minor>`, minimum `1.1`) parsed from the user agent;
the desktop shell is recognised by its Go bindings instead
(`web/app.js:181-210`, `apps/capacitor.config.ts`). The TUI never loads
`web/app.js` and talks the API directly, so this gating does not apply to it —
the TUI implements its own saved-server UI in `internal/tuiclient/config.go`.
The capability version is **separate** from the release tag and is not driven by
`DOMINION_VERSION`.

### Screens

1. **Server prompt** — `host[:port]` + HTTP/HTTPS toggle + saved-server list.
2. **PIN login** — same lock/error semantics as `web/index.html:119-129`.
3. **Session view** — list (pinned first, attached/window hints), status,
   active shell.
4. **Dialogs** — new session, kill confirm (with the "attached" warning),
   settings (dark/light).
5. **Actions** — new, kill, lock, logout, refresh, quit.

Config reuses `~/.config/dominion/client.json` (the AppImage's saved-server
format, `apps/desktop/main.go:46-88`) as a shared address book; an added
`theme` key is additive. PIN is prompted per run and never persisted.

### Attach bridge

Selecting a session calls `tview.Application.Suspend(func(){…})`:

- set the local terminal raw via `golang.org/x/term`, read initial size
- dial `GET /api/attach?session=&cols=&rows=` with the cookie
- pump stdin→WS (binary) and WS→stdout
- `SIGWINCH` → `{"type":"resize","cols":…,"rows":…}` (the contract in
  `internal/ptybridge/bridge.go:137-166`)
- detach key `Ctrl-]` resumes the TUI
- WS code `4001` → login; `1001` → reconnect/exit

In-process `Suspend` is preferred over a literal re-exec, so the auth cookie
stays in memory and is never written to disk or passed via an fd.

### Dependencies

Add to root `go.mod`: `github.com/gdamore/tcell/v2`,
`github.com/rivo/tview`, `golang.org/x/term`. Reuse `gorilla/websocket`. This is
the largest dependency growth the module has taken; it is the accepted cost of
the tview choice.

### Testing

- `internal/tuiclient/api_test.go` — `httptest`: login sets cookie, sessions
  parse, create/kill, 401 surfacing.
- `config_test.go` — `client.json` round-trip, including the new `theme` key and
  compatibility with the desktop schema.
- `attach_test.go` — drive the byte-pump over pipes + a `gorilla` test upgrader;
  verify resize JSON encoding and close-code propagation.
- `go vet ./...` and `go test ./...`.

### Phase 1 — One version everywhere

Two distinct versions, handled separately:

- **Release version** (`DOMINION_VERSION`, from the tag `vX.Y.Z`):
  - root `release.sh` already takes it positionally; thread it into the APK.
  - `apps/build-client.sh` reads `DOMINION_VERSION` instead of the hardcoded
    `0.1` (default `0.0.2`).
  - server and TUI get `-ldflags "-X main.version=…"` and a `-version` flag.
  - APK `versionName`/`versionCode` injected into the generated
    `apps/android/` project in `build-variant.sh`.
- **Capability version** (`apps/capacitor.config.ts`, e.g. `dominion-shell/1.1`):
  independent of the release tag; bump only when the shell's feature set changes.
- Add `CHANGELOG.md`; use the tag's section as release notes.

### Phase 2 — Refactor the scripts

Root `release.sh` becomes: option parsing (`--server-only`, `--no-publish`) →
build stage (server, TUI, then `apps/build-variant.sh` for APK + AppImage) →
stage into `dist/` → write `SHA256SUMS` (excluding itself) → optional publish
stage. Keep the existing `gh`-then-`GITHUB_TOKEN` dual auth path so local runs
still work.

Specific changes required for a clean runner (see the blockers in Phase 3):

| Change | File | Detail |
|--------|------|--------|
| Version + ldflags | root `release.sh`, `apps/build-client.sh` | `DOMINION_VERSION`; `-X main.version` on server + TUI |
| Build/publish split | root `release.sh` | `--no-publish`: build → stage `dist/` → `SHA256SUMS` → exit |
| TUI asset | root `release.sh` | build `./cmd/dominion-client-tui` |
| Self-healing Android project | `apps/build-variant.sh` | `[ -d android ] \|\| npx cap add android` |
| Version injection | `apps/build-variant.sh` | patch generated `versionName`/`versionCode` |
| CA injection | `apps/build-variant.sh`, `apps/android-overlay/sync-ca.sh` | accept an explicit `DOMINION_CA` path |
| Canonical CA asset | root `release.sh` | copy `ca.pem` into `dist/` + `SHA256SUMS` |

Final naming (as shipped; the AppImage keeps the plain `.AppImage` suffix since
the release is linux/amd64-only):

| Artifact | Asset name |
|----------|-----------|
| server | `dominion_<ver>_linux_amd64` |
| TUI | `dominion-client-tui_<ver>_linux_amd64` |
| APK | `dominion_<ver>.apk` |
| AppImage | `dominion_<ver>.AppImage` |
| CA | `ca.pem` |

`get.sh` needs only `dominion_<ver>_linux_amd64`, `run.sh`, `.env.example`,
`dominion.service`; the client assets are referenced by docs/scripts only.

### Phase 3 — Release pipeline (`.github/workflows/release.yml`)

A thin wrapper that invokes the same `release.sh` used locally:

```yaml
on:
  push: { tags: ['v*'] }
  workflow_dispatch:
    inputs: { version: {default: "0.0.2"}, publish: {type: boolean, default: false} }
permissions: { contents: write }        # overrides restrictive repo defaults
concurrency: { group: release, cancel-in-progress: false }
```

Job `release` on `ubuntu-latest`:

1. `actions/checkout@v4`.
2. Go 1.24 (cache); Node 22 (cache: `apps/package-lock.json`); JDK 17 temurin
   (**must** have `jlink` — `apps/README.md:85`).
3. `android-actions/setup-android@v3` + `sdkmanager "platforms;android-34"
   "build-tools;34.0.0" "platform-tools"`.
4. `apt-get install -y libgtk-3-dev libwebkit2gtk-4.1-dev imagemagick`.
5. Cache `~/.gradle` (wrapper pins Gradle 8.2.1).
6. `echo "$CA_B64" | base64 -d > ci-ca.pem` (secret `DOMINION_CA_PEM_B64`;
   base64 avoids newline mangling).
7. `DOMINION_CA=ci-ca.pem DOMINION_VERSION=${GITHUB_REF_NAME#v} ./release.sh`
   with `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}`; `workflow_dispatch` with
   `publish=false` appends `--no-publish`.
8. `actions/upload-artifact@v4` for `dist/` (inspect before/without publishing).

Notes:

- **Publishing needs no extra secret**: `gh` is preinstalled and
  `release.sh:68-72` prefers it; `gh` reads `GH_TOKEN`.
- **No FUSE**: `build-desktop.sh:92` uses `--appimage-extract-and-run`.
- **CA secret required**: if `DOMINION_CA_PEM_B64` is unset the job fails fast
  with a clear message. This keeps official APKs trusting the maintainer's
  server.
- Fixes "no releases" permanently and removes the local `gh`/token blocker.

## Out of scope

- The release work adds no runtime behavior changes to the server or web UI.
- The in-flight Android capability gating and desktop identity/icon work belong
  to the Phase 0 freeze, not to the release plumbing.
- No release-signed APK (debug APK for now).
- No per-component release streams (one combined release).
- No arm64 assets (amd64 only; ARM hosts build from source).
- No change to how `get.sh` fetches `run.sh`/`.env.example`/`dominion.service`
  (they come from the tagged commit, not the release assets).

## Operational prerequisite (maintainer)

Before the first pipeline run, create the repository secret
`DOMINION_CA_PEM_B64` from the server's CA:

```sh
base64 -w0 ~/.config/dominion/ca.pem
```

Store the output as the secret. Without it, the workflow fails at the CA step.
This is what lets official APKs keep trusting the maintainer's server over
HTTPS.
